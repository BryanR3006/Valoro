# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**Valoro**: Flask + SQLite (Flask-SQLAlchemy) + APScheduler web app (AdminLTE UI, Jinja templates) that sends **SMS (Infobip)** and **email (esmsv.com API)** to bases read from **Google BigQuery** (project `capable-arbor-209819`) or, for SMS, from an Excel file. Code, comments, logs and UI are in Spanish — keep new code in the same language and style. `README.md` has the user-facing reference (config keys, flow, files).

## Running

```bash
pip install -r requirements.txt
python app.py                      # http://localhost:5000 (PORT env var overrides)
```

- The app runs with `debug=False, use_reloader=False` on purpose: the reloader spawned two processes → two schedulers → every job ran twice. **After editing any `.py` file, restart the process manually.**
- BigQuery credentials: `config/google_key.json` (service account) or gcloud ADC — see `conexion_bigquery.get_bigquery_client()`.
- `config.json` is not in git (Infobip and email API keys, general parameters, SMS `senuelos`). New copies start from `config.example.json` (same structure, empty values) and fill the keys by hand. Code must read credentials from `config.json`, never hardcode them.
- There is no test suite, linter or build step. `consulta_segura.py`, `services/sms_exclusiones.py`, `services/variables.py`, `services/sms_horarios.py` and `datos_personales.py` are free of Flask/DB/network so they can be exercised with fake objects; keep new pure rules in the same style.

### Test copy mode (`modo_prueba.py`)

`APP_COPIA_PRUEBA=1` runs the app as a test copy: it must run from its own folder and on a port other than 5000 (checked in `proteger_arranque_copia_prueba`, called at the top of `app.py` *before* `backend` is imported). It skips the BigQuery writes of the scheduled jobs (SMS status polling, Infobip→`Temporal.SmsInfobip_Valoro` sync) and does not reload pending SMS/email programaciones at startup. It does **not** block manual SMS/email sends.

## Architecture

- **`backend.py`** — importing it has side effects: creates the Flask `app`, configures SQLite (`app.db`), logging (`app_log.txt`, `execution_log.txt`, and per-channel `logs/sms.log` / `logs/email.log` via `logger_sms` / `logger_email`), loads `config.json`, and **starts the global `BackgroundScheduler` (timezone `America/Bogota`)** with the SMS status polling, console heartbeat and log maintenance jobs. `APP_NOMBRE` (shown in the UI through a context processor) lives here. Everything else imports `app`, `db`, `scheduler` from here.
- **`app.py`** — all HTTP routes plus scheduler jobs registered at import time: per-programación SMS jobs `sms_simple_<id>` (DateTrigger) / `sms_recurrente_<id>` (every 10 min, sends once a day at `hora_inicio`; with `intervalo_minutos` + `hora_fin` it checks every minute and repeats during the day, e.g. 08:00 every 2 h until 18:30 — rules in `services/sms_horarios.py`, same calc in `static/js/horarios.js`), `email_programado_<id>`, startup reloads (`sms_recargar_programaciones`, `email_recargar_programaciones`), `sms_infobip_sync` / `sms_infobip_sync_dia`. No blueprints. When editing/removing a programación, also replace/remove its job by id (`agendar_programacion_sms`, `_sms_desagendar`).
- **`database.py`** — SQLAlchemy models: `ProgramacionSms` (SMS programaciones, states `pendiente`/`enviado`/`completado`/`error`/`cancelado`, `ultimo_error`, `ultimo_enviados`), `MensajeOperacion` (SMS templates, table `Mensajes_`, grouped by `Momento` and optional `Etapa` 1–4, with user-assigned `IdMensaje`/`IdCampana` that the SMS constructor copies into the send and that replace the row's `Id Mensaje`/`Id Campaña` in Infobip's `callbackData` (`ids_en_callback`, so the Infobip report shows them) and go in `campaignReferenceId` — also stored per `ProgramacionSms` (`id_mensaje`/`id_campana`); the old `Operador`/`Tipo`/`Categoria`/`Operadores` columns are no longer used), `PlantillaEmail` (`momento`), `ProgramacionEmail` (table `programaciones_email`). No migration tool: new columns go in the model **and** in the matching `_ensure_*_columns()` (`_agregar_columnas` runs `ALTER TABLE ... ADD COLUMN` on startup).
- **Email programaciones** live in SQLite (`ProgramacionEmail`, table `programaciones_email`, id = uuid string), like SMS; BigQuery is only read for the base (`consulta_sql`). The old BigQuery table `Temporal.ProgramacionEmail_Valoro` is no longer used. `tipo` = simple/recurrente, scheduled **the same way as SMS**: simple = `fecha_programada` (job `email_programado_<id>`, DateTrigger); recurrente = `hora_inicio` + optional `intervalo_minutos`/`hora_fin` + `fecha_fin` (job `email_recurrente_<id>`, every 1 or 10 min, `turno_a_enviar` via `_email_turno`; back to `pendiente` after each turn, `completado` after `fecha_fin`). In a recurrente `fecha_programada` is when it was created/edited: earlier turns never go out. Old recurring rows without `hora_inicio` use the time of `fecha_programada` (`hora_recurrente()`). Form/edit use the same fields as SMS (`crearHorario` in `config_email.html`). CRUD: `GET/PATCH/DELETE /api/email/programaciones/<id>`, cancel `POST /api/email/cancelar/<id>`; jobs via `_email_agendar` / `_email_desagendar`. Each run stores `ultimo_enviados` and `fecha_ejecucion` (Colombia time).
- **Send flow** (SMS and email): query → read-only check + BigQuery dry run (`consulta_segura`, `bigquery.fetch_sms_query_rows`, real BigQuery message via `mensaje_error_bigquery`) → template (`{{Columna}}`; SMS templates from the constructor, filtered by **momento** del cliente, or typed) → Infobip link shortening (`urlOptions.shortenUrl`) → blacklists (`listas_negras.py`) and same-day duplicates → send or schedule. If the blacklist can't be read, the send is cancelled.
- **Pages**: send and programaciones are separate pages that share one template: `/config-sms` and `/sms/programaciones` render `config_sms.html` with `modo` `enviar`/`programar` (the SMS list + edit modal is `templates/sms/_lista_programaciones.html`); `/config-email` and `/email/programaciones` render `config_email.html` the same way. Elements of one mode only carry `solo-enviar` / `solo-programar` (hidden by `valoro.css`).
- **Historial de programaciones** (`/programaciones`, `templates/programaciones.html`): SMS and email in one table, modeled on the old robot's "Programaciones Terminator" view (Python_Qnt-): view message, whether it ran, edit/cancel/retry/delete through each channel's API (email retry: `POST /api/email/programaciones/<id>/reejecutar`).
- **Galería de plantillas** (`/plantillas`, `templates/plantillas.html`): gallery of every email template (scaled thumbnail, large view with ‹ ›) and SMS template (phone bubble, length/parts) with full CRUD through each channel's API: create/edit (live preview), duplicate (SMS copies start inactive), activate/deactivate, delete. Email templates can only be deleted if never used (`DELETE /api/email/plantillas/<id>` → 409 if `usos`); editing a used one saves "<nombre> v2". Filters by momento, text and inactive. "Usar" opens `/config-email?plantilla=<id>`, which preselects it; `/plantillas#sms` opens the SMS tab.
- **Historial de envíos** (`/envios`, `templates/envios.html`, queries in `historial_envios.py`): everything sent, one row per send. SMS = `SmsLog` rows with the same campaign/user/template, batches less than 5 min apart merged (`juntar_lotes`), state from `SmsInfobip_Valoro` by `message_id` (fallback: `SmsLog.resultado`), cost with `COSTO_SQL`. Email = `EmailLog` grouped by `bulk_id` (esmsv campaign id); the real status comes live from esmsv (`/api/envios/email/<id>/estado`). Origin (manual vs programación) is inferred in `_origen_envio` (`EjecucionProgramacion` or a programación with that campaign and a turn at that time) since `SmsLog.programacion_id` is never filled. Recipients: `/api/envios/detalle`, CSV: `/api/envios/exportar`.
- **Home** (`/`): `/api/inicio/resumen` returns today's totals from `SmsLog`/`EmailLog` (grouped by `campana`), and today's programaciones with `estado_hoy` (`corrio`/`pendiente`/`error`): SMS and email both from SQLite (`fecha_ejecucion`, `ultimo_enviados`, `ultimo_error`). BigQuery errors go in `avisos` (via `mensaje_error_bigquery`); the SQLite part always answers. Each programación also carries `turnos`: every run of the day from `EjecucionProgramacion` (table `ejecuciones_programacion`, written by `registrar_ejecucion` in both scheduled jobs: `enviado`/`sin_datos`/`error`, rows from the query, sent, excluded) plus expected turns with no run (`pendiente`/`no_corrio`, rule `turnos_del_dia` in `services/sms_horarios.py`). `/api/inicio/saldo`: Infobip balance (`/account/1/balance`) and SMS cost today/month from `Temporal.SmsInfobip_Valoro` (`COSTO_SQL`), emails from `EmailLog`; esmsv has no balance endpoint.
- **Email send check**: esmsv answers "ok" to `campaign/send` even when the campaign doesn't go out, so `enviar_campana_email` reads the campaign back (`verificar_campana_enviada`: must exist, not be `Draft`) before writing `EmailLog`. Create/send wait 120 s; on a timeout creating, the campaign is looked up by name + list. Empty base = `SinDestinatariosEmail` (scheduled: `sin_datos`, not error; recurring keeps going). **Contacts** (the slow part): `enviar_campana_email` loads them in parallel (`email.max_workers`, default 5) with one API call each — `contacts/edit` for existing ones (found in `directorio_contactos`, read 100 per page when that's cheaper than looking them up one by one) and `contacts/create` for new ones; existing contacts are never deleted/recreated (keeps history and unsubscribes) and empty columns clear stale fields. `EmailClient` uses one session per thread, 6 s connect timeout and 4 connect retries (the API sometimes refuses connections; Windows waits 21 s). A contact that still fails is reported in `fallidos` and the rest go out. `guardar_email_log` inserts 300 rows per parameterized INSERT. Progress goes to the live log via `progreso`.
- **Errors shown to users** (`services/errores.py`, pure): routes and jobs show `mensaje_error(exc)` — a short Spanish message with the cause (no connection, API limit, no balance, rejected key, BigQuery query error, or the app's own clear message) and the service; the full exception always goes to the logger (`logger.exception`). A message that is already final (e.g. "Infobip didn't answer in time: the batch may have gone out") is wrapped with `marcar_claro` so it isn't replaced by the generic connection text. Infobip batches (`enviar_lote`) raise the cause and are retried only when they surely didn't go out (no connection, 429, 503) — never after a read timeout (could duplicate); messages Infobip rejects (`groupName REJECTED`, e.g. no credits) don't count as sent and the reason goes in the result `message` (`resumen_envio_sms`). Read-only esmsv calls (`EmailClient._leer`) retry on slow responses too, and the last custom fields read are cached (`email_campos_cache.json`, git-ignored) for when the API doesn't answer.
- **Recurring programaciones keep going after a failed turn** (SMS and email): the turn is marked in `ultimo_intento` before sending, a failure leaves it `pendiente` with `ultimo_error` (clear message) and an `error` ejecución, and that turn is not retried (it could duplicate what went out) — the next turn runs normally. Simple ones still go to `error`. "Reintentar" clears `ultimo_intento` so the current turn can go again.
- **Sending window** (`horario_envio_desde`/`horario_envio_hasta` in `config.json` → `general_parameters`, editable in Parámetros generales, default 07:00–18:00 Colombia time, `get_horario_envio()`): outside it no SMS or email goes out, manual or scheduled. Checked in three places: (1) start — manual send routes (`_fuera_de_horario()`, strict) and scheduled jobs (with `MARGEN_FIN_ENVIO_MIN` = 15 min, so a job that checks every 10 min still sends the 18:00 turn); (2) **right before sending** — `enviar_sms_desde_filas` before the Infobip batches and `enviar_campana_email` at the start and again before creating the campaign (with the 15-min margin): on 24/10/2026 the PC went to sleep in the middle of the 14:00 email turn and, on waking at 19:48, the job finished and sent it; (3) creating/editing programaciones — hours outside the window are rejected (`_error_hora_programada`, also "Hasta las"), and turns outside it are dropped (`horas_del_dia`/`turno_a_enviar` with `ventana`). The end hour is included (the 18:00 turn goes out). Rules in `services/sms_horarios.py` (`fuera_de_horario`, `error_hora_de_envio`).
- **Config**: `app.py` calls `load_config()` on each use, so edits to `config.json` (e.g. a new email `api_key`) apply without a restart.
- **Momentos**: free text with suggestions (`MOMENTOS_SUGERIDOS` + saved ones, `_momentos()` in `app.py`). SMS templates: `/api/sms/mensajes?momento=&etapa=&activos=1`.
- **Link del mensaje**: SMS templates (`Mensajes_.Link`), the constructor and each `ProgramacionSms.link` carry a link that replaces `{{Link}}` in every row and in the señuelos (`aplicar_link_mensaje` in `services/sms_excel.py`, applied before validation and again at execution), so the query doesn't need a Link column; Infobip shortens it (`shortenUrl`).
- **Señuelos** (`config.json` → `infobip.senuelos`) get every SMS send and are never excluded (blacklist or same-day duplicates, with or without `confirmar_reenvio`): `filtrar_permitidos` in `sms_service.py` is the one filter for send, validate and schedule.
- **Template variables** (SMS and email): `{{Variable}}` is matched to a query column by `services/variables.buscar_columna` — ignoring case, accents, spaces, `-` and `_` (`{{valor_a_pagar}}` = `Valor a Pagar`), and the client's name has aliases (`nombre`, `Nombre Cliente`, `customer_name`…: any of them fills any other). SMS `construir_mensaje`/`validar_variables`/exclusion rules and email `construir_contenido`/`validar_variables_plantilla`/`campo_de` all use it. SMS señuelos get their message from `fila_senuelo`: the template's columns from the first client with the señuelo's own name, phone and link (only those columns go in their callbackData). Previews show clients first and one señuelo (`items_vista_previa`).
- **Señuelos de email** (`config.json` → `email.senuelos`: `[{"email", "nombre"}]`) work like the SMS ones: `filtrar_destinatarios` appends them (row copied from the first client, with their email and name in the name columns, `es_nombre`) only when at least one client is left, and they are never excluded. Used by send, validate and scheduled sends.
- **Users and login** (`usuarios.py`, same as Omnic's): every route needs a session (`guardia`, before_request), except `/login`, `/logout` and `/static/`. Profiles: `admin` (everything, plus `/usuarios` and `/registro`) and `analitica` (sees everything but cannot open `BLOQUEADAS_LECTORES` — send/program/template/config pages — and can only POST to `ESCRITURAS_LECTORES`). **A new operation page (send, program, configure) must be added to `BLOQUEADAS_LECTORES`**; any new non-GET route is admin-only by default. The layout shows menu items with `puede_ver(url)` and hides operation buttons for non-admins with CSS. `registrar` (after_request) stores every non-GET and download in `RegistroAccion` and `logs/acciones`, `logs/usuarios/<usuario>` (`registro_logs.py`). Creating sends, programaciones and templates takes the responsable from the session (`registro_logs.usuario_sesion()`), the form field is only a fallback. Users are shared between PCs through `Temporal.Valoro_Usuarios` (`usuarios_bq.py`, jobs `usuarios_sync_arranque` / `usuarios_sync`; read-only in the test copy). The `admin` user is seeded with `usuario_admin_clave` (or `Admin123`) and must change it on first login. Sessions are signed with `secret_key` from `config.json` (or `SECRET_KEY`). Omnic also has a `comercial` profile; Valoro uses only Admin and Analítica for now.
- **`services/`**— `sms_service.py` (Infobip, SmsLog, polling), `sms_excel.py`, `sms_exclusiones.py`, `email_service.py`, `email_client.py`.
- **Design** (`static/css/valoro.css`): dark green sidebar (lime logo reads there), white/light content, dark text. Brand: lime `#adff00`, dark greens `#071f0f`/`#0c2a17`/`#143a22`, medium green `#2f7d1e`, gold `#f9c400`; gradients in `--grad-oscuro`/`--grad-verde`/`--grad-acento`. Never lime text on a light background.
- **SMS dashboard** — `dashboard_sms.py`, `infobip_sync.py`, `infobip_logs.py` (`/dashboards`). Reads `Temporal.SmsInfobip_Valoro`, filled only from Valoro's Infobip account (`infobip.api_key` in `config.json`). `Temporal.SmsInfobip` belongs to QNT (its robot, another Infobip account): never read or write it from Valoro.
- Required fields: `_faltantes_sms` / `_faltantes_email` in `app.py` return the names of the missing fields; the templates check the same names before calling the API.

## Working notes

- `app.db` is the live database; back it up before schema or data changes.
- **Console = clear lines only** (`consola.py`, pure): the terminal and the home page live log (`/api/recent_logs`, in memory) show only `backend.log_activity` lines (logger `actividad`, `FiltroClaro`), as `HH:MM:SS  message` in one line, without tracebacks (`FormatoClaro`). Write one line per step that matters, not technical detail: "⏰ SMS 'X' · turno 14:00: consultando BigQuery…", "📤 … 144 registros · 112 excluidos (…) · enviando 36 SMS a Infobip…" (the `progreso` callback of `enviar_sms_desde_filas`, `resumen_filtros_sms`), "✅/⚠️/⏭️/❌ … result". Errors start with ❌ and warnings with ⚠️ (that sets the panel colour). Everything else (`logger`, `logger_sms`, `logger_email`, libraries, warnings via `captureWarnings`) only goes to `app_log.txt` and `logs/sms.log` / `logs/email.log`. The heartbeat job (`console_message_interval_seconds`) prints the pending turns of the day (`texto_pendientes` in `services/sms_horarios.py`) only when it changes; uncaught job errors get a line from the `EVENT_JOB_ERROR` listener. Log files use `ArchivoRotativo` (if Windows doesn't let it rotate, it keeps writing and retries in 10 min) and one shared handler per area file: one handler per logger on the same file blocked its rotation (WinError 32 on every line). `log_task` also writes `execution_log.txt`.
- **SmsLog only holds SMS that went out**: `enviar_sms_desde_filas` saves only the SMS of batches Infobip accepted and not rejected (`REJECTED`). `verificar_duplicados` counts every SmsLog row of the day, so saving unsent SMS would make the next turn skip those clients.

## Team workflow

The repo is maintained by **rodri** and **bcrodriguez**. This file is the shared memory of the Claude Code sessions: when a team rule changes, change it here and push it.

- **Ownership.** SMS, email and the shared core → bcrodriguez (with rodri). Before touching an area someone else is working on, ask your user to check with them.
- **Branches.** Every change goes in its own branch off an up-to-date main branch, small commits, then a PR or merge. Pull before starting and before pushing. Never force-push the main branch.
- **No credentials in git.** `config.json` (Infobip/email keys, `senuelos`), `config/google_key.json`, `app.db` and the logs are ignored and stay local to each copy. New config keys go in `config.example.json` with empty values. Scripts read credentials from `config.json`, never hardcoded. Before every commit check `git diff --cached` for tokens, passwords or client data (phones, emails, names).
- **One production app.** Only one instance with the scheduler may run against Infobip/email (production machine, port 5000). Each `app.db` holds its own SMS and email programaciones. Two running apps with active programaciones = duplicate messages. `app.py` refuses to start if another app is already running from the same folder (`instancia_unica.py`: exclusive lock on `app.lock`, released by the OS when the process dies); on 21/10/2026 an app forgotten since 16/10 was running the same programaciones and blocking `app_log.txt` rotation (`Logging error ... WinError 32`).
- **Developing.** Use the test copy mode (`APP_COPIA_PRUEBA=1`, `PORT=5001`, different folder) with an `app.db` that has no active SMS programaciones and without real send credentials when possible. After editing any `.py`, the app must be restarted by hand; tell your user when a change needs a restart.
